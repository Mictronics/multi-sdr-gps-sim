# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build

```
make all HACKRFSDR=yes PLUTOSDR=yes LIMESDR=yes   # each flag optional; iqfile backend is always built
make test
make clean
```

Flat Makefile, C11, no linter. `make test` runs seven unit tests, linked against `gps.c`, its modules (`orbit.c`, `rinex.c`, `model.c`, `navmsg.c`, `download.c`) and `sbas.c` with the GUI stubbed (except `tests/test_almanac.c`, which links only `almanac.c` and mocks `download_file`: source order, retries, rejected HTML/short files, the cached `almanac.sem`, on `tests/data/sample_almanac.al3`) (`tests/stubs.c`) and run from the repository root: `tests/test_nav.c` checks the navigation message that `eph2sbf` and `generateNavMsg` write against the IS-GPS-200 bit positions (health, almanac pages, page 25 configuration, reserved page SV IDs, the page 17 special message, leap seconds, ephemeris rounding, TOW at the week end, page by time), `tests/test_fifo.c` that the FIFO loses no block, `tests/test_model.c` the troposphere values, `tests/test_sbas.c` the SBAS layer (CRC-24Q, convolutional code, MT9 and MT17 fields, the message schedule, the MT18/MT26 grid against RTKLIB's IGP bands, and that a MOPS receiver model on our grid gives the simulated Klobuchar slant delay within 1 m), and `tests/test_rinex.c` checks `readRinex` and `ephSelect` on `tests/data/sample_rinex3.rnx`, a trimmed real IGS merged file sorted by satellite, plus files built from its records that reproduce layouts which broke the ephemeris selection (lone uploads next to a regular update, more than a dozen epochs, duplicates), and `tests/test_signal.c` (which `#include`s `gps.c` for its static channel functions and links without `gps.o`) that the code phase of GPS and SBAS channels runs on across the 0.1 s blocks (each block interpolates from the previous range to the current one, so the only jump is up to 1e-4 chip from double rounding of the time of week) and that `--cn0` gives the noise sigma and the requested C/N0 within 0.5 dB. Deps: libm, pthread, libcurl, libz, ncurses/panel, plus libhackrf, libiio + libad9361 and/or LimeSuiteNG's legacy API wrapper (`lime/LimeSuite.h`, `-llimesuiteng-legacyapi`, no .pc file) when the matching SDR flag is set. Backends are compiled in via `-DENABLE_HACKRFSDR` / `-DENABLE_PLUTOSDR` / `-DENABLE_LIMESDR`.

Objects track header dependencies (`-MMD`) and are rebuilt when `HACKRFSDR`, `PLUTOSDR`, `LIMESDR` or `OPT` change (`.build-flags`). The default is `-O2`; use `make OPT=-O0` for debugging.

Run example: `./gps-sim -f -s now -l 48.0,10.0,500 -r iqfile` (downloads current data; with your own files use `-e nav.gz` instead of `-f`) (see README for all options; `help.h` holds the usage text). `-r` selects the SDR backend (`none|iqfile|hackrf|plutosdr|limesdr`). Nav files may be gzipped RINEX 2 or 3 (`-3`). `-f` downloads the nav file (NOAA CORS for RINEX 2, BKG for RINEX 3; with `-s now` a NOAA file that lags behind the start time is replaced by BKG's file of the day) and the almanac over HTTPS instead (sources in `almanac_sources[]` in `almanac.c`: NAVCEN current, Celestrak, NAVCEN daily archive; a valid download replaces `almanac.sem`, which is used when all fail).

The program needs a terminal of at least 120x31 (except with `--no-tui`) and writes `iqdata.bin` in the working directory with `-r iqfile`. Without `-f` the almanac is read from `almanac.sem` in the working directory; one more than 4 weeks away from the scenario time is rejected, so use `--disable-almanac` with old nav files.

## Architecture

Derived from Takuji Ebinuma's gps-sdr-sim. The program synthesizes GPS L1 C/A baseband IQ on the fly and streams it to an SDR, with an ncurses TUI.

- `gps-sim.c` — `main`, option parsing, and the global `simulator` struct (`gps-sim.h`) shared across threads. Starts the GPS thread, then the selected SDR backend and the TUI.
- `gps.c` — the simulation core: C/A codes (`codegen`), ephemeris/almanac handling, satellite channel allocation, code phase, and IQ sample generation. Types shared by all modules are in `gps.h`; each module below has its own header with the prototypes:
  - `orbit.c` — vectors, GPS time (`subGpsTime`, `incGpsTime`, `date2gps`), coordinate conversions (`xyz2llh`, `ltcmat`, ...) and `satpos`.
  - `rinex.c` — RINEX parsing (`readRinex` handles v2 and v3 into an `eph_table_t` holding every record per satellite, so satellite-ordered merged files work; `ephSelect` gives each satellite the record closest in time within `EPH_MAX_AGE`, used at the start and at every 30 s update), `ionoDefaults` and the `LEAP_DEFAULT_*` values (`rinex.h`).
  - `model.c` — Klobuchar ionosphere (also for the SBAS grid, `sbasIonoUpdate`), troposphere, and the pseudorange (`computeRange`, `rangeFromPos`).
  - `navmsg.c` — navigation message: `eph2sbf` (subframes 1-5 with all almanac pages), parity, `generateNavMsg`.
  - `download.c` — `download_file` (curl) and the nav file download for `-f`.

  `gps.c`: `gps_thread_ep` is the producer thread: a short orchestrator over the steps `initUserPosition`, `loadEphemeris`, `loadMotionFile`, `selectStartTime`, `loadAlmanac` and `initChannels`, then per 0.1 s block `moveUser`, `updateChannels`, `generateSamples`, `queueSamples` (`NUM_IQ_SAMPLES` at 3 MS/s, see `sdr.h`), plus `updateNavigation` every 30 s. They share a `gps_ctx_t`.
- `sbas.c` — SBAS L1 message layer: the GEO table `sbas_geo[]`, framing with CRC-24Q, the rate 1/2 convolutional encoder, and `sbas_message`, which gives the message type and content for each second (MT1/2-4/25 with zero corrections, MT7, MT9, MT10, MT17, MT18/MT26 from Klobuchar). The GEO channels themselves live in `gps.c` (`allocateSbas`, `sbasStart`, `sbasFill`; a 60 s symbol buffer, refilled 30 s at a time in `updateNavigation`).
- `fifo.c` — ring buffer of `NUM_FIFO_BUFFERS` IQ buffers connecting the GPS producer thread to the SDR consumer thread.
- `sdr.c` / `sdr.h` — backend-neutral SDR interface; `sdr_hackrf.c`, `sdr_pluto.c`, `sdr_lime.c`, `sdr_iqfile.c` implement it, each with its own TX thread that drains the FIFO.
- `almanac.c` — reads the SEM-format almanac (`almanac.sem`); `eph2sbf` in `navmsg.c` scales it into the subframe 4/5 pages.
- `gui.c` — curses/panel TUI: status windows and interactive position changes in real time.

Things that are easy to get wrong when changing the stream (found on real phones, not by unit tests):
- Ephemeris and almanac in the stream must agree (they differ by 1-2 km for fresh data). `-s now` therefore only shifts a nav file's times to the start time when fewer than `COVER_MIN_SATS` satellites have a record within `EPH_MAX_AGE` of it (an old file); shifting fresh data put the satellites ~26,000 km away from the almanac and phones distrusted them.
- All channels send the same subframe 4/5 page, (frame count of the week mod 25) + 1, as real satellites do; per-channel page counters starting at page 1 did not match the time. A receiver has every page after 12.5 minutes; when a given page (e.g. page 18, iono/UTC/leap seconds) airs depends on the start time.
- Missing iono/UTC/leap data in a RINEX header is filled by `ionoDefaults` with neutral values (leap seconds `LEAP_DEFAULT_DTLS`, 18 s; update it when a new leap second is introduced). Groups the file provides are kept and applied to the simulated delays too.
- The simulator adds the broadcast (Klobuchar) ionosphere and a troposphere delay (Saastamoinen zenith delay, Black-Eisner mapping), the models phones correct for; `--disable-iono` turns off both. Without the troposphere a phone's height came out 7-15 m low. The mapping must stay bounded at the horizon: Saastamoinen's 1/sin(el) gave a setting satellite a range jump of kilometres per 0.1 s and crashed the sample loop. The carrier follows the code range, so the ionosphere delays both instead of advancing the carrier; this only matters for carrier-phase (ADR/RTK) use.
- `-s now` is the system clock (UTC) plus the leap seconds, read after the download; a time given with `-s` is taken as GPS time, like the RINEX epochs.
- Ephemeris and almanac values are encoded with `round()`: RINEX prints whole LSB multiples to ~13 digits, and a cast was one step low for about half the fields.
- When the simulation ends (`-d`, end of a motion file, GPS thread error) the main loop calls `sdr_close` as soon as the FIFO has drained, before `x`: the TX threads only wait on the FIFO, so the Pluto kept its TX LO on (an unmodulated carrier on L1) and HackRF/Lime stayed in TX until `x`. `sdr_close` then switches to the "none" handler, so a second close and gain keys are no-ops.
- `generateSamples` wraps the carrier phase with `floor` and masks the sine table index, so a bad range cannot index outside the table; `fifo_enqueue` once dropped every block queued behind another (0.6 s lost at each start).
- Pluto TX samples are 12 bit in the upper bits of 16 (`le:S16/16>>0`, see `iio_info -u ip:pluto.local`); `sdr_pluto.c` clips and shifts. Phones track at -50 dB attenuation on the Pluto, 14 dB gain on the HackRF (cable with 60 dB attenuation, amplifier off).
- LimeSDR streams `LMS_FMT_I12` (12 bit, not shifted); `sdr_lime.c` clips to ±2047 because the 12 bit link would wrap. The TX port is the one whose `LMS_GetAntennaBW` covers L1 (Band1 on the Mini), searched from index 1: index 0 is "None" and the wrapper throws a C++ exception for it. It needs LimeSuiteNG `develop` built from source (README, "LimeSuiteNG for LimeSDR"); the 25.1 packages hang in `LMS_SendStream` on a Mini v1. In NG, `LMS_SetGaindB` sets the TX PAD (0-52 dB) but `LMS_GetGaindB` adds 12, so the gain is never read back. Calibration runs at `LIME_CAL_GAIN` (40) because at low gain the test signal is too weak. The sample rate must be exact: with the default oversampling (32) CGEN lands at 383.999996 MHz and the rate 333 ppb low while the LO is right, so code and carrier disagree by ~100 m/s; the Samsung A33 then had noisy C/N0 and no fix while the Pixel tracked. `LIME_OVERSAMPLE` 4 gives exactly 48 MHz and both phones lock (A/B tested). The Mini's VCTCXO runs 1.4 ppm slow (measured against an OCXO HackRF), which is harmless because LO and sample clock share it; do not correct it with `-p`, that shifts only the LO. A Pixel tracks at `-g 5` (25-35 dB-Hz) on the 60 dB cable.
- The Samsung A33 shows no stable almanac ("A") flag even under the real sky; the Pixel 4 does, so use the Pixel to check almanac changes.
- SBAS is checked on a u-blox NEO-M8T (phones track the GEOs but Android does not report SBAS use). The stream needs enough symbol transitions: zero corrections plus null messages (MT63) gave 15 % and the M8T never synchronised, 17.5 % still failed, our MT18/MT26 grid in the free slots gives about 25 % (real EGNOS 27.5 %). The 63 slots of the schedule in `sbas_message` are filled with MT18/MT26 whenever there is a grid; keep them filled when changing it.
- A receiver searches only the GEOs it knows (EGNOS lists 121 and 136) until an MT17 from a GEO it tracks announces more; without MT17 a cold M8T stayed on 136 alone and showed no SBAS system. MT17 can only help when several GEOs are sent, so `--sbas 150` alone is never acquired.
- The M8T keeps SBAS corrections after the GEO is gone and reports "diff 1" from them, so a run after another one proves nothing: cold-start it first (UBX-CFG-RST, navBbrMask 0xFFFF, resetMode 2). CFG-SBAS alone does not switch SBAS off, CFG-GNSS does (it restarts the GNSS). A badly seated SMA connector cost about 10 dB and gave the HackRF a level-dependent pseudorange bias of up to 34 m (15-21 m fix error, real sky replayed through it too): when the level drops at an unchanged gain, reseat the connectors before suspecting the signal. With good connections the GPS-only fix is 0.2 m (Pluto -45), 0.5 m (Lime -g 10), 1.7 m (HackRF -g 20); the README table has the residuals.
- The 8-bit path (`iq_buff >> 4` in `queueSamples`, HackRF and the default iqfile) clips at ±127; it used to wrap, and SBAS at +6 dB then killed reception. Headroom is small: a 70 s run at 48 N 10 E peaks at ±97 without SBAS and ±120 with three GEOs (RMS about 21-24).
- `--cn0` adds Gaussian noise (σ `NOISE_SIGMA` 400 per component, a 4096-value table indexed by a fixed-seed xorshift, so runs stay reproducible) and scales every gain by `level`, A = σ·√(2·C/N0/fs) at 20200 km and boresight. In that mode the per-channel samples are rounded (`sampleRound`) instead of truncated: at 25 dB-Hz a satellite is only ~6 units and truncation cost 1 dB. Without `--cn0` `level` is 1 and nothing is rounded, so `iqdata.bin` stays byte-identical. A 70 s run at 45 dB-Hz peaks at 126 (8 bit) / 2004 (16 bit) with no clipping, RMS about the same as without noise. On the rig (Pluto, 60 dB, M8T) the simulated noise only dominates the receiver's own at about `-g -25`, 20 dB above the no-noise working point; there the M8T reports 0.9/1.6/1.9/2.8 dB below `--cn0` 30/40/45/50 (README table), with the elevation shape within ±0.3 dB. 0.34 dB of that is our point-sampled code (one chip value per sample correlates worse with the band-limited ideal code; offline check, averaging the chip over the sample would leave 0.05 dB but delays the code by half a sample); `CODE_SAMPLING_LOSS_DB` adds it back in `--cn0` mode, after those measurements.
- `sbas_geo[]` in `sbas.c` follows the gps.gov L1 C/A PRN assignments; update it like `LEAP_DEFAULT_DTLS` when GEOs move or change. `--disable-sbas` must keep `iqdata.bin` byte-identical to a build without SBAS.

Regression runs: the output for a given `-e` file and `-s` time is deterministic, so compare `iqdata.bin` checksums before and after a change (byte-identical unless the change is meant to alter the signal). Run them headless, `./gps-sim --no-tui -e nav.gz -s ... -d 70 -r iqfile`: status goes to stderr and the program exits once the FIFO has drained, so the whole file can be compared (it holds `-d`×10 − 1 blocks; the sample loop starts at 1, as in gps-sdr-sim). To test the TUI itself without a terminal: `script -qec "stty cols 130 rows 30; exec ./gps-sim ..." /dev/null &` and SIGTERM; `pkill -x` only matches names of up to 15 characters, and `pkill -f` with the binary's name also matches the shell running it. Cores of crashed runs are kept by systemd: `coredumpctl gdb <pid>`.

Data flow: RINEX/almanac → `gps.c` channel + nav-message state → IQ buffers → FIFO → SDR TX thread. Position comes from `--geo-loc`, a motion file (`-m`, e.g. `circle.csv`), `--target` or TUI input.

The working directory also collects untracked build artifacts (`*.o`, `gps-sim`) and data files (`*.gz` RINEX files, `almanac.sem`, `iqdata.bin`); downloads with `-f` overwrite `rinex2.gz`, `rinex3.gz` and `almanac.sem` there. `circle.csv` is a tracked sample motion file for `-m`.
